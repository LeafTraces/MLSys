02 · SLIDES 8–9

Data Layout：矩阵在内存里到底长什么样？

矩阵是二维的，内存地址是一维的。Stride 决定从逻辑坐标到物理位置的映射。

ROW-MAJOR
addr(A[i,j]) = base + (i·N+j)·s
A00A01A02A10A11A12

同一行相邻 j 连续。这里 s 是每个元素所占的字节数，N 是列数。

STRIDED VIEW
offset = i·stride₀ + j·stride₁

以 3×4 的行主序矩阵为例，其元素步长可写成 (4,1)。转置得到形状 4×3 的视图，步长则是 (1,4)，通常无须复制数据。

Zero-copy ≠ Zero-cost

Transpose 修改形状与 stride 可以不搬数据，但后续 kernel 如果要求连续访问，可能访问低效或需执行一次 contiguous() 复制。第 9 页强调的正是这个取舍。

03 · SLIDES 12–14

没有分块时：为什么 A 和 B 都是 n³ 次加载？

注意：Slides 算的是 C = dot(A, B.T)，因此内层是 A[i][k] * B[j][k]，而不是常见的 B[k][j]；B 的每一行也是参与点积的向量。

来源 Slides 第 14 页 · 理想化的无缓存复用模型
for (i = 0; i < n; ++i)
  for (j = 0; j < n; ++j) {
    register float c = 0;
    for (k = 0; k < n; ++k) {
      register float a = A[i][k]; // 取 A 的 1 个元素
      register float b = B[j][k]; // 取 B 的 1 个元素
      c += a * b;
    }
    C[i][j] = c;
  }
总内层迭代
n · n · n = n³

每个 i、j 组合都有 n 次 k。

A + B 的读入量
n³ + n³ = 2n³

每次 k 取一个 A 和一个 B 元素。

寄存器中概念上的数值
a + b + c = 3

这是 Slides 的简化标量驻留数，不是真实机器寄存器分配结果。

读入量与时间不是一回事

这里的 2n³ 是演示模型中的元素加载次数。真实硬件通常存在 cache、预取、向量化和编译器调度，不能把 2n³ 直接等同于实际 DRAM 访问次数，更不能直接推断运行时间。

04 · SLIDE 15 · CORE

寄存器分块：一次算一整个 C 小矩形

不要先盯代码。先想象你负责给 C 里的一个矩形“刷颜色”：不是逐像素完成，而是同时维护 v₁ 行 × v₂ 列的所有累加器。

三块积木 · 对应第 15 页
A tile
v₁ × v₃

来自 A 的 v₁ 行和 k 维度上的 v₃ 列。

B tile
v₂ × v₃

B 按行存储：v₂ 行和 v₃ 列；计算时用 B tile 的转置。

C accumulator
v₁ × v₂

这 v₁v₂ 个 C 元素一直留在寄存器中，沿 k 维累加。

Ctile ← Ctile + Atile · BtileT

维度检查：(v1 × v3) @ (v3 × v2) → (v1 × v2)。如果这个 shape 不对，后面的整个成本模型也就无从谈起。

FIGURE 01 · 一次 Tile 相乘的形状

A 和 B 的 tile 在一个 k-block 内相乘，完成 2×3×2 次乘加；随后沿 k 前进并累加到同一块 C。

把三个索引分别看成三种“方向”

v₁：输出行数

一个 A 元素要服务于 C 里多少不同列？答案取决于 v₂。

v₂：输出列数

一个 B 元素要服务于 C 里多少不同的行？答案取决于 v₁。

v₃：归约分块深度

每次从 k 维处理多少元素；它影响单次工作块大小及寄存器负担。

最反直觉、也最重要的一点

A 的读入次数由 v₂ 减少，B 的读入次数由 v₁ 减少。 不是笔误：A 在相同输出行、不同输出列间共享；B 在相同输出列、不同输出行间共享。

第 15 页代码换成更好读的伪代码

// 假设 n 可被 v1、v2、v3 整除；A、B 已按块组织
for (i = 0; i < n/v1; ++i)        // 选一块输出行
  for (j = 0; j < n/v2; ++j) {      // 选一块输出列
    register float c[v1][v2] = {0};
    for (k = 0; k < n/v3; ++k) {  // 沿归约维滑动
      register float a[v1][v3] = A_tile(i,k);
      register float b[v2][v3] = B_tile(j,k);
      c += dot(a, transpose(b)); // v1×v2 个累加器
    }
    store_C_tile(i,j,c);            // 最后写回一次
  }

对应第 15 页。这里 register 与预先分块的数组布局是课程用于讲解的抽象，不保证 C/CUDA 编译器严格照此分配寄存器。

05 · SLIDES 16, 20 · CORE

成本计算：为什么是 n³/v₂ + n³/v₁？

把公式背下来很容易忘。我们只用一个方法：循环总次数 × 每次搬运多少元素。下面每个因子都可以在第 15 页的三重循环中找到。

先数一共执行多少次内层 k-block

T = nv₁ · nv₂ · nv₃ = n³v₁v₂v₃

它表示 (i,j,k) 这组三个块索引一共会遍历多少次，不是矩阵乘法的 FLOPs。

A 的元素加载

1

每轮加载 A tile

含有 v₁v₃ 个 float。

2

乘以总轮数 T

n³/(v₁v₂v₃) × v₁v₃

LA = n³v₂

v₁、v₃ 被约掉，剩下的是 v₂。

B 的元素加载

1

每轮加载 B tile

含有 v₂v₃ 个 float。

2

乘以总轮数 T

n³/(v₁v₂v₃) × v₂v₃

LB = n³v₁

v₂、v₃ 被约掉，剩下的是 v₁。

LA+B = n³/v₂ + n³/v₁与第 16 页一致：该量是简化模型中的加载元素次数，尚未换算成字节或时间

寄存器容量怎么计算？

A 常驻块
v₁ · v₃
B 常驻块
v₂ · v₃
C 累加器
v₁ · v₂
R = v₁v₃ + v₂v₃ + v₁v₂ 计量单位：浮点元素；如均为 FP32，概念存储容量为 4R 字节
注意官方 Slides 第 20 页的分母不一致

第 16 页的 A 加载量是 n³/v₂，但第 20 页相同位置写为 n³/v₃。按照第 15 页代码，每轮 A tile 是 v₁×v₃，乘三重循环次数并化简，得到的应是 n³/v₂。因此本讲义按第 16 页和独立推导处理，第 20 页写法应视作疑似排版笔误。

为什么 v₃ 在加载量公式中“消失”了？

把 v₃ 加倍，k 方向的块数量减半，但每次加载的 A/B 子块也在 k 方向加倍。因此在这个理想化模型里两个因素抵消。但 v₃ 加大仍会增加寄存器占用，也可能影响真实循环开销、向量化、寄存器溢出和吞吐。

你应该能独立复述的物理原因

固定一块输出 C 时，A 的每个数可以参与当前 C 的 v₂ 个输出列；B 的每个数可以参与当前 C 的 v₁ 个输出行。所以 A 被复用 v₂ 次，B 被复用 v₁ 次。

我们用一个真的有数值的例子：n=6, v₁=2, v₂=3, v₃=2。要计算 C 前两行、前三列的一块输出，需要沿 k 走 3 次。每次只取 A 的 2×2 橙色区域与 B 的 3×2 绿色区域，更新 C 中蓝色的 2×3 小块。

08 · SLIDES 17–18

缓存分块：让整个行块先住进 L1

上一层用寄存器维护微型输出块；这一层改用 L1 容纳更大的“面板”。Slides 选择一次从 A 取 b₁×n，从 B 取 b₂×n。

缓存层循环结构
for (i = 0; i < n/b1; ++i) {
  L1 a = A_row_panel(i); // b1×n
  for (j = 0; j < n/b2; ++j) {
    L1 b = B_row_panel(j); // b2×n
    C_tile(i,j) = dot(a,b.T);
  }
}

这里 a 放在 j 循环外：只加载一次，就能和所有 B 面板配对。

DRAM → L1 加载量 · 逐项计数
LA = (n/b₁) · b₁n = n²
LB = (n/b₁) · (n/b₂) · b₂n = n³/b₁

依然是一个不对称结构：A 面板在 j 循环中复用；B 面板随外层 i 再次读取。

容量限制不能忽略

Slides 第 18 页写的是 b₁·n + b₂·n < L1 cache size。这里左边如果按 FP32 元素数计量，应乘以 4 才能和以 Byte 表示的缓存容量比较：4n(b₁+b₂) < L1_bytes。这仍是忽略其他工作数据、缓存冲突和共享占用的理想条件。

DRAM → L1 总读取 = n² + n³/b₁

为什么第 18 页还要求 b₁ % v₁ == 0 与 b₂ % v₂ == 0？因为下一步还要把 L1 中的大块进一步切成小的寄存器块，必须在这个简化版本中整齐地嵌套。

来源：Slides 第 17–18 页。本讲义把隐含的元素/字节单位换算单独说明。

两级分块合体：多级内存各做各的事

第 19 页标题是 Putting it Together。最重要的不是多了一串循环，而是两个层次的复用共同存在。

DRAM

原课件写的 Load Cost 是什么？

Cost ≈ tL1 · (n³/v₂ + n³/v₁) + tDRAM · (n² + n³/b₁)

第 19 页用 l1speed 和 dramspeed 作为每次元素取数的时间权重，记成加权成本。这里我们改写为 t_L1 与 t_DRAM 避免把“速度更大”误读为“时间成本更大”。它不是精确的时间预测器，因为现代 CPU/GPU 可能在流水线中重叠计算与搬运，还受带宽、并发、缓存命中、数据布局等影响。

展开：第 19 页的四层循环究竟在做什么？
// 第一级：先让 A、B 行面板尽量停留在 L1
for (i = 0; i < n/b1; ++i) {
    a = load_L1(A_panel(i));
    for (j = 0; j < n/b2; ++j) {
        b = load_L1(B_panel(j));
        // 第二级：将面板的输出行/列拆成寄存器 tile
        for (x = 0; x < b1/v1; ++x)
            for (y = 0; y < b2/v2; ++y) {
                register c[v1][v2] = {0};
                for (k = 0; k < n; ++k) {
                    register ar[v1] = a[x][k][:];
                    register br[v2] = b[y][k][:];
                    c += ar @ br.T;
                }
                store(c);
            }
    }
}

在这份第 19 页例子中，寄存器层沿每个 k 单独取 v₁ 和 v₂ 个元素，相当于取 v₃=1 的直观形式；本讲义前面的 v₃ 更一般。

10 · SLIDES 20–22

举一反三：真正要寻找的是“谁不依赖哪个循环”

Slides 第 21 页把复用规律总结成：A[i][k] 不依赖 j，因此沿 j 分块可以复用 A。第 22 页把问题扩展到卷积。

Matrix Multiply

C[i,j] = Σk A[i,k] · B[j,k]

A 不依赖 j → 在 j 的 tile 内复用 A；B 不依赖 i → 在 i 的 tile 内复用 B。

Convolution

Y[b,co,y,x] = Σci,ry,rx X[b,ci,y+ry,x+rx] · W[co,ci,ry,rx]

Weight 不依赖输出空间坐标 y,x（同一输出通道 co）；Input 不依赖输出通道 co。因此卷积也有共享和复用机会。

方法论：拿到任意张量表达式，按三步走

① 写出所有循环维度；② 对每个输入元素，圈出“不出现”的循环索引；③ 沿这些维度并行计算多个输出，让同一份输入服务更多次乘加。再检查寄存器/L1 容量是否允许。

11 · SCIENTIFIC CAUTION

重要：为什么上面的结果不是“真实加速比”

这是读系统论文和做项目必须养成的谨慎性。Slides 故意用抽象“dram”“l1cache”“register”推导逻辑成本，目的在于说明复用机制，而不是描述某个 GPU 的最终执行轨迹。

Slides 简化模型真实实现还要考虑带来的含义
每次取数都按相应层成本计算缓存命中、预取、访存合并、共享缓存实际 DRAM 流量可能远低于 naïve 2n³
寄存器占用 R = v₁v₃+v₂v₃+v₁v₂编译器分配、向量打包、寄存器 spill、其他临时量R 是概念 footprint，不是编译器报告的真实 register count
加大 tile 可提高复用寄存器压力、线程 occupancy、指令依赖Tile 并不是越大越好
读入时间与元素数量线性带宽上限、并发、流水线、传输与计算重叠减少 4× 流量不代表程序必然快 4×
忽略 C 的额外访存输出写回 n²、某些实现读旧 C、边界/对齐完整成本应按算法与写回策略加入相应数据量

和 Roofline Model 接起来

Attainable FLOPs/s ≤ min(Peak FLOPs/s, Bandwidth · Arithmetic Intensity)

按照本讲义示例，把浮点乘加记作 2 FLOPs，FP32 记为 4 Byte，则只计 A/B 读流量：naive 的简化 AI ≈ 0.25 FLOP/Byte；register tile 的简化 AI ≈ 2 / [4·(1/v₁+1/v₂)] FLOP/Byte。这两个值都取决于选定的内存层级与忽略项，不能直接当作芯片计数器结果。

工程实践里用什么确认？

先写正确的 reference implementation → 微基准测 latency 和吞吐 → 使用 profiler 查访存/计算指标 → 在不同尺寸与 layout 上复测 → 再讨论瓶颈是否转移。

正确：n³/v₂。每个 A tile 的 v₁v₃ 个元素被用来生成 v₂ 列 C，因此单个 A 元素在输出列方向被复用 v₂ 次。
Q2 · 保持 v₁、v₂ 不变，只把 v₃ 从 2 增加到 4。按照 Slides 第 16 页简化模型，什么会变化？
正确：寄存器驻留数增加。v₃ 在 n³/v₂+n³/v₁ 中约掉了；但 R=v₁v₃+v₂v₃+v₁v₂ 明显随着 v₃ 增加。
Q3 · L1 Cache Tiling 中，为什么 B 的 DRAM→L1 加载量是 n³/b₁？
正确：B 随每个外层 i 的 A 行块重新加载。计算：(n/b₁)·(n/b₂)·(b₂n)=n³/b₁。
Q4 · 把读入次数减少到原来的四分之一，是否可以推断真实运行时间也变为四分之一？
正确：不可以。计算、缓存、带宽、指令开销、并发以及资源占用都会影响最终性能。理论数据流量是分析工具而非真实 speedup。

纸笔推导（先别展开答案）

设 n=64，v₁=4，v₂=8，v₃=2。请计算：① A 加载量；② B 加载量；③ 总加载量是 naive 的几分之几；④ 同时驻留多少个 FP32 元素。

查看完整标准答案与计算过程

A = 64³/8 = 32,768；B = 64³/4 = 65,536；合计 98,304 元素。Naive 为 2×64³ = 524,288 元素，因此新旧比为 3/16 = 18.75%，理论读入元素数减少 81.25%。寄存器驻留元素数：4×2 + 8×2 + 4×8 = 56 个 FP32，即概念容量 224 Byte。这不是实际寄存器使用报告。
